## ADDED Requirements

### Requirement: Update a warehouse receipt with transactional stock reversal

The system SHALL allow an authorized user to update an existing warehouse receipt. All stock mutations MUST occur inside a single `prisma.$transaction`. The update MUST reverse the receipt's original stock impact on its original `lotProduct` (subtract the original `soLuongNhap`), then apply the new impact on the target `lotProduct` (add the new `soLuongNhap`), which MAY be a different `lotProduct` if the warehouse/lot/product changed. Denormalized fields (`tenKho`, `tenLo`, `tenSanPham`, `donViTinh`) and the `soLuongTruoc`/`soLuongSau` snapshots MUST be recomputed from the current stock at update time; earlier or later slips MUST NOT be retroactively recalculated.

#### Scenario: Update receipt quantity on the same lot product
- **WHEN** an authorized user updates a receipt's `soLuongNhap` from 10 to 15 on the same `lotProduct`
- **THEN** the system subtracts the original 10 and adds 15, leaving the `lotProduct.soLuong` net +5 compared to before the edit
- **AND** the receipt's `soLuongTruoc`/`soLuongSau` reflect the recomputed values and the operation commits atomically

#### Scenario: Update receipt to a different lot product
- **WHEN** an authorized user changes a receipt's warehouse/lot/product to a different `lotProduct`
- **THEN** the system subtracts the original `soLuongNhap` from the old `lotProduct` and adds the new `soLuongNhap` to the new `lotProduct` within one transaction
- **AND** the receipt's denormalized `tenKho`/`tenLo`/`tenSanPham`/`donViTinh` are updated to match the new target

### Requirement: Delete a warehouse receipt with transactional stock reversal

The system SHALL allow an authorized user to delete an existing warehouse receipt. Within a single `prisma.$transaction`, the system MUST subtract the receipt's `soLuongNhap` back from its `lotProduct.soLuong` and then remove the receipt record.

#### Scenario: Delete a receipt reverses its stock addition
- **WHEN** an authorized user deletes a receipt that added 20 units
- **THEN** the system subtracts 20 from the `lotProduct.soLuong` and deletes the receipt in one transaction

### Requirement: Update a warehouse issue with transactional stock reversal

The system SHALL allow an authorized user to update an existing warehouse issue. Within a single `prisma.$transaction`, the update MUST reverse the issue's original stock impact on its original `lotProduct` (add the original `soLuongXuat` back), then apply the new impact on the target `lotProduct` (subtract the new `soLuongXuat`), which MAY be a different `lotProduct`. Denormalized fields and `soLuongTruoc`/`soLuongSau` MUST be recomputed from current stock at update time.

#### Scenario: Update issue quantity on the same lot product
- **WHEN** an authorized user updates an issue's `soLuongXuat` from 5 to 8 on the same `lotProduct`
- **THEN** the system adds back the original 5 and subtracts 8, leaving `lotProduct.soLuong` net -3 compared to before the edit, committed atomically

### Requirement: Delete a warehouse issue with transactional stock reversal

The system SHALL allow an authorized user to delete an existing warehouse issue. Within a single `prisma.$transaction`, the system MUST add the issue's `soLuongXuat` back to its `lotProduct.soLuong` and then remove the issue record.

#### Scenario: Delete an issue refunds its stock deduction
- **WHEN** an authorized user deletes an issue that removed 12 units
- **THEN** the system adds 12 back to the `lotProduct.soLuong` and deletes the issue in one transaction

### Requirement: Negative-stock guard on edit and delete

The system MUST reject any update or delete that would drive a `lotProduct.soLuong` below zero. On violation, the system MUST throw `ValidationError` and the transaction MUST roll back so no stock or slip changes persist. For warehouse issues, the rejection message MUST convey insufficient stock (e.g. "Số lượng tồn kho không đủ...").

#### Scenario: Editing an issue upward beyond available stock is rejected
- **WHEN** an authorized user edits an issue so the new `soLuongXuat` exceeds what the target `lotProduct` can supply after reversing the original deduction
- **THEN** the system throws `ValidationError`, rolls back the transaction, and leaves stock and the issue unchanged

#### Scenario: Deleting a receipt whose stock was already issued out is rejected
- **WHEN** an authorized user deletes a receipt but reversing its addition would make `lotProduct.soLuong` negative
- **THEN** the system throws `ValidationError`, rolls back, and leaves stock and the receipt unchanged

### Requirement: Lock special slips from edit and delete

The system MUST prevent editing or deleting slips that are managed by another workflow. A receipt or issue linked to a supply request (`supplyRequestId != null`) MUST be locked. A warehouse issue that is auto-generated by a `MaterialEvaluation` (has a linked `materialEvaluation`) MUST be locked. Attempting to update or delete a locked slip MUST throw `ConflictError` with a message identifying the reason (supply-request-linked, or material-evaluation-generated). Stock and records MUST remain unchanged.

#### Scenario: Editing a supply-request-linked receipt is blocked
- **WHEN** an authorized user attempts to update or delete a receipt with a non-null `supplyRequestId`
- **THEN** the system throws `ConflictError` ("Không thể sửa/xóa phiếu gắn với yêu cầu cung cấp") and makes no changes

#### Scenario: Editing a material-evaluation-generated issue is blocked
- **WHEN** an authorized user attempts to update or delete an issue that has a linked `materialEvaluation`
- **THEN** the system throws `ConflictError` ("Không thể sửa/xóa phiếu xuất do đánh giá nguyên liệu tạo") and makes no changes

### Requirement: getAll exposes an isLocked flag

The list endpoints for receipts and issues MUST return an `isLocked` boolean per record. For receipts, `isLocked = (supplyRequestId != null)`. For issues, `isLocked = (supplyRequestId != null) OR (linked materialEvaluation exists)`; the issue query MUST include the `materialEvaluation` relation (selecting only its id) to compute this.

#### Scenario: List marks locked slips
- **WHEN** a client fetches all receipts or issues
- **THEN** each record includes `isLocked`, true for supply-request-linked slips and for material-evaluation-generated issues, false otherwise

### Requirement: Edit and delete endpoints are role-restricted

The system MUST expose `PUT /:id` and `DELETE /:id` for both warehouse receipts and warehouse issues, restricted to the same roles allowed to create them: `ADMIN`, `DEPARTMENT_HEAD`, `TEAM_LEAD`. Controllers MUST return the standard API shape `{ success, message, data }` and map domain errors to HTTP status: 400 for `ValidationError`, 404 for not-found, 409 for `ConflictError`.

#### Scenario: Unauthorized role cannot edit or delete
- **WHEN** a user without `ADMIN`/`DEPARTMENT_HEAD`/`TEAM_LEAD` calls PUT or DELETE on a slip
- **THEN** the request is rejected by authorization middleware

#### Scenario: Domain errors map to HTTP status codes
- **WHEN** an update/delete throws `ValidationError`, a not-found error, or `ConflictError`
- **THEN** the controller responds with 400, 404, or 409 respectively and `{ success: false, message }`

### Requirement: Slip edit and delete are available in the warehouse tabs

The warehouse receipt and issue tabs MUST provide an Edit action and a Delete action for each slip row, alongside the existing view-detail action. Both actions MUST be hidden when the slip's `isLocked` is true. Edit MUST reuse the create modal in edit mode (prefilled fields, "Cập nhật" submit label) and call the update endpoint. Delete MUST confirm with the user, call the delete endpoint, then refresh the slip list and warehouse stock and invalidate the warehouses query cache.

#### Scenario: Locked slip hides edit and delete
- **WHEN** a slip row has `isLocked === true`
- **THEN** the row shows only the view-detail action; Edit and Delete are not rendered

#### Scenario: Deleting a slip refreshes data
- **WHEN** the user confirms deletion of an unlocked slip
- **THEN** the tab calls the delete endpoint, then re-fetches slips and warehouses and invalidates the warehouses query cache
